# 온톨로지 V4.8 설계 검증

검증일: 2026-09-18 · 코드 기준: `39b78ec` · 범위: 정의 SoT, 독립 전달 코드, XLSX 명세, ZIP, CSV 적재기, 감사기, 시간축·지연확장 모듈.

**판정: 도메인 모델의 기본 구성은 갖춰져 있으나, 현재 V4.8을 일관된 배포 계약으로 확정하기에는 식별자·전달본·검증 기준 보완이 필요하다.** 아래 결과는 로컬 정적 대조와 합성 입력 재현이다. 운영 DB 데이터의 정합성, 추론 정확도, 실제 원본 복원 성공률은 이번 검증으로 보증하지 않는다.

## 1. 확인된 구성과 장점

- 6계층(Source, Case, Person, Object, Location, Event), 노드 25종, 관계 72종, 활성 관계 70종, 통합 추론 규칙 13종.
- Source를 독립 객체로 두고 사건·사람·객체·장소·이벤트를 구분한다. 송금/통화/접속/메시지 등을 이벤트 노드로 표현해 시각과 원본 키를 연결할 수 있다.
- `registered_to`와 `uses_id`는 명의와 실제 사용을 분리한다. 이는 식별자와 사람을 즉시 동일시하지 않는 데 유용하다.
- 현재 SoT와 **압축 해제된** 전달 Python의 ENTITIES, NODE_ID_STANDARD, EDGE_META_SCHEMA, GDB_LABEL_MAP 및 관계 핵심 계약은 일치한다. 전달본이 제거한 `source_types`, `semantic_relation`은 배포 목적의 축약이므로 그 차이 자체를 오류로 세지 않았다.
- 최신 사건 키 승격은 현재 코드와 전달 Python에 반영됐다: `vt_case.incdnt_no`가 정경 식별자이고 `flnm`은 보조 속성이다. CSV 로더도 사건 노드를 `incdnt_no`로 생성한다.

### 식별자 계약의 해석

`ENTITIES.properties`는 명시적인 primary-key 목록이 아니다. 따라서 속성이 둘이라는 이유만으로 복합키라고 단정하지 않았다. 다만 계좌의 `bank_cd`, 지갑의 `blockchain`은 엔티티에 선언돼 있는데 정경 키는 각각 `account_no`, `wallet_addr` 하나다. 번호/주소의 유일성 범위를 결정하고 **명시적인 `key_fields` 배열**로 표현해야 한다. 현재처럼 `'(platform, id_val)'` 문자열을 파싱하는 방식은 도구 간 구현 편차를 만든다.

인물의 `psn_id`가 없을 때 이름만으로 합치기보다는 출처별 임시 ID를 발급하고 이름은 검색 속성으로 유지하는 방안을 권고한다. 계좌는 기관 코드와 번호의 조합, 지갑은 체인·네트워크와 주소의 조합을 검토하되, 확정은 원천 기관의 식별 규칙과 대조해야 한다.

## 3. 감사 결과가 보증하지 않는 항목

외부 감사기 `handoff/ontology_v4.8/code/audit_ontology_v48.py`를 직접 확인했다.

- 실패 조건은 주로 라벨·관계명·deprecated·domain/range다. 필수 키 누락과 출처 누락은 경고다.
- 키의 중복, 빈 문자열, 복합키 전체의 동시 충족을 검사하지 않는다.
- 출처 보유율은 **노드만** 검사한다. 엣지의 `source_id`, 실제 `vt_src.src_id` 참조 존재, `edge_id` 유일성, `evidence_edge_ids`의 참조 유효성은 검사하지 않는다.
- `EDGE_META_SCHEMA`의 필수·조건부 필수 규칙은 주석이다. `verified=True`이면 검증자·검증시각이 있어야 한다는 조건, confidence 범위, enum, 날짜 역전 등은 이 감사기로 집행되지 않는다.
- `Any`는 범위 검사를 생략한다. 현재 domain에 Any인 관계는 8종으로 README 설명과 일치하지만, range의 Any까지 포함하면 10종이다. 의도한 개방 관계와 임시로 범위를 넓힌 관계를 구분할 필요가 있다.
- 정경 라벨 외에 영문 개념명도 허용하며 `ag_` 접두 라벨은 무시한다. 엄격한 저장 라벨 정책과는 차이가 있다.

따라서 기존 전달 문서의 운영 스냅샷 “위반 0”은 **해당 감사기가 세는 위반 0**으로 해석해야 한다. 전체 무결성 통과나 현재 운영 상태를 뜻하지 않는다.

## 4. 시간·집약·동일성 설계 검토

### 시간축

`valid_from/to`와 `rec_created`의 분리는 유용하다. 하지만 생성시각 하나와 현재 유효구간만으로 과거 정정 전 상태까지 재현되는 완전한 이중시간 이력 모델이 자동 성립하지는 않는다. 정정 버전, 기록 유효 종료, 대체 관계 또는 append-only 이력 정책이 필요하다. 이는 현재 조사 범위에서 확인되지 않은 설계 계약이다.

일 단위 반개구간을 유지한다면 마지막 관측일 다음 날을 배타적 종료로 삼는 방법이 있다. 다만 최초·최종 관측 사이에 계속 사용했다는 추정과 실제 개별 접속 사실은 구분해야 한다. `ip_role_current`는 코드상 “마지막 구간”이며 오늘 유효한 구간을 찾는 함수가 아니다. UI와 질의에서 “현재”를 쓰려면 의미를 명시해야 한다.

동일 role 인접 구간을 병합할 때 인원 수는 최댓값을 보존한다. 따라서 그 값을 병합 구간 모든 시점의 정확한 인원 수로 해석하면 안 된다. 또한 다수 실체가 공유한 IP라는 통계만으로 `call_center`라는 실제 용도를 확정하기는 어렵다. 통계적 후보와 확인된 역할을 구분하는 것이 적절하다.

### 집약 및 원본 복원

- SoT의 aggregation_level 값은 `raw|hourly|daily`; XLSX 메시지 속성 사전은 `individual|aggregated`. 저장 해상도와 집약 여부를 별도 필드로 나누거나 단일 enum으로 정리해야 한다.
- 등록부의 집약 키는 `(subject_id, time bucket, event_type)`이다. 목적지·출처 등이 다를 때 하나로 묶을지, 묶더라도 원본 간 대응을 어떻게 유지할지 명시되지 않았다. 이는 실제 오병합을 재현한 결과가 아닌 설계상 검토 항목이다.
- `lazy_expansion.py`는 판정과 조회 대상 명세를 만드는 순수 모듈이다. `sample_event_ids`는 최대 20개이며 이것만으로 전체 원본을 복원할 수 없다. 전체 집합을 식별하는 쿼리 조건이나 매핑이 필요하다.
- `vt_msg` bridge는 SMS 테이블로 고정돼 있고 채팅 병행은 주석이다. 원본 종류별 라우팅 및 전체 복원 성공은 DB 어댑터를 포함해 별도 검증해야 한다.

### 동일성 및 추론

Person·DigitalID·Phone의 모든 조합을 같은 domain/range로 허용하는 `same_as`는 사람 자체의 동일성, 계정의 동일성, 같은 사람이 사용하는 서로 다른 식별자의 연결을 혼동할 수 있다. 확정 동일성, 후보 일치, 사용·소유 연결의 의미와 병합 조건을 분리해야 한다. 특히 유사한 아이디 문자열은 동일 실체의 확정 근거와 같지 않다.

W3C OWL의 개체 동일성은 같은 개체를 가리킨다는 강한 의미다. 현재 property graph의 사용자 정의 `same_as`가 자동으로 OWL 동일성이라는 뜻은 아니며, RDF 교환이나 추론 연동 시 무조건 매핑하면 안 된다. [OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)

## 5. 외부 표준과 대조한 보완 방향

현재 구현은 Python으로 정의한 property graph 도메인 스키마다. OWL 파일이 없다는 사실만으로 결함이라고 판단하지 않았다. 필요한 것은 실행 가능한 제약 계약이다.

- SHACL은 타입·필수 개수·범위·열거값 등의 제약과 검증 결과를 분리해 표현한다. 이를 설계 기준으로 삼아 AgensGraph용 검사에 같은 제약을 구현하거나, RDF 교환이 필요할 때 SHACL을 생성할 수 있다. SHACL 자체는 RDF 그래프 검증 표준이므로 현재 DB에 그대로 실행되는 것은 아니다. [W3C SHACL](https://www.w3.org/TR/shacl/)
- PROV-O는 Entity·Activity·Agent와 유래·생성·책임 관계를 구분한다. 현재 source_id를 출발점으로 원본 레코드, 적재/추론 실행, 수행 주체, 파생 근거를 연결하는 모델을 보강할 수 있다. 출처 필드가 존재하는 것과 추적 가능한 증거 계보가 완성되는 것은 별개다. [W3C PROV-O](https://www.w3.org/TR/prov-o/)

## 6. 권고하는 수정 순서와 완료 기준

1. **V4.8 배포 기준 고정:** 5종 식별자 필드와 사건 키를 확정하고 Python·XLSX·ZIP을 같은 소스에서 생성한다. 버전, 커밋, 생성시각, 파일 해시를 manifest로 남긴다. 의미가 바뀐 동일 버전 재배포를 피한다.
2. **엄격 감사 모드:** 필수 키/출처 누락·중복·참조 단절을 실패로 만들고 경고와 실패를 분리한다. Object 및 union 타입을 확장하고 Any 사용 정책을 명시한다.
3. **적재 식별 범위 정리:** 동명이인, 은행별 동일 계좌번호, 플랫폼별 동일 ID를 각각 다른 노드로 유지하는 합성 회귀 사례를 통과시킨다. 재적재 중복 여부도 검증한다.
4. **시간 계약 정리:** 마지막 관측일 포함, 빈 구간, 종료된 관계, 정정 이력, 시간대와 정밀도 사례를 검증한다.
5. **관계·추론 의미 확정:** XLSX deprecated 상태, same_as 허용 대상과 검토 상태, 집약 enum 및 원본 복원 계약을 통일한다.
6. **운영 읽기 전용 검증:** 위 기준 확정 후 실제 DB에서 중복·고아 참조·시간 역전·필수 메타 누락을 집계한다. 관계 72종 중 실제 적재된 종류와 미검증 종류를 구분해 보고한다.
