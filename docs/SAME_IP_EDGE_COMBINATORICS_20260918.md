# 같은-IP 계정 쌍: 직접 엣지를 두지 않는 이유 (조합론적 근거)

> 타 기관 코멘트 "id 간 동일ip사용 엣지가 없어 조회 요구가 없음"에 대한 설계 근거.
> 결론: 엣지 부재는 **조합 폭발을 피하기 위한 의도된 설계**이며, 조회는 vt_ip 매개로
> 완전히 대체된다. 수치는 로컬 `ccop_ep_integrated` 실측(2026-09-18).

---

## 1. 문제 정의

`vt_id` 계정이 어떤 IP를 썼다는 관계는 원본 엣지 `used_ip` 로 저장한다.
"같은 IP를 쓴 두 계정"을 **직접 엣지(same_ip)** 로 미리 만들어 둘지, 아니면 **질의 시 유도**할지가 쟁점이다.

기호:
- IP `p` 를 공유한 계정 수를 **Nₚ** 라 한다.
- 원본 `used_ip` 엣지 총수 = **Σₚ Nₚ** (계정–IP 연결의 합)
- same_ip 로 만들 계정 쌍 총수 = **Σₚ C(Nₚ, 2) = Σₚ Nₚ(Nₚ−1)/2**

## 2. 핵심: 선형 vs 이차

| 대상 | 규모식 | 성질 | 실측값 |
|---|---|---|---|
| 원본 `used_ip` (저장 중) | **Σ Nₚ** | 계정 수에 **선형** O(n) | 15,197 |
| 파생 `same_ip` (저장 시) | **Σ C(Nₚ,2)** | 한 IP 안에서 **이차** O(N²) | 7,812 |

한 IP에 계정이 **N개** 붙으면 그 IP가 만드는 쌍은

  **C(N, 2) = N(N−1)/2 ≈ N²/2**

즉 계정이 **선형으로** 늘어도 쌍은 **제곱으로** 늘어난다. IP 하나의 기여가 N² 이므로,
공유 계정이 많은 IP(콜센터·공용망) 하나가 전체를 지배한다.

## 3. 실측 — 편중과 성장률

### 3.1 IP당 계정 수와 쌍 (상위)

| IP | 공유 계정 Nₚ | 그 IP가 만드는 쌍 C(Nₚ,2) | 전체 대비 |
|---|---|---|---|
| 122.54.197.66 | 83 | **3,403** | **43%** |
| 122.54.197.65 | 48 | 1,128 | 14% |
| 124.111.91.100 | 27 | 351 | 4% |
| 182.224.169.251 | 20 | 190 | 2% |
| 124.62.150.182 | 15 | 105 | 1% |

**상위 1개 IP가 전체 쌍의 43%, 상위 3개가 62%, 상위 10개가 70%.**
소수의 고공유 IP가 same_ip 엣지의 대부분을 만든다(멱함수형 편중).

### 3.2 분포의 볼록성 (왜 집중이 위험한가)

C(N,2) 는 N 에 대한 **볼록(2차) 함수**다. 총 계정 수(Σ Nₚ)가 같아도, 계정이 **한 IP에
집중될수록** 쌍 총합 Σ C(Nₚ,2) 은 급증한다(옌센 부등식).

- 분산 극단: 모든 IP가 Nₚ=1 → Σ C = 0 (쌍 없음)
- 집중 극단: M개 계정이 한 IP → C(M,2) ≈ M²/2 (쌍 폭발)

실측에서도 **13,159개 IP 중 11,670개(89%)는 Nₚ=1 이라 쌍을 전혀 안 만들고**, 쌍은
전부 소수의 고공유 IP(N≥2, 1,489개)에서 나온다.

### 3.3 성장률 — 지금 총량이 작아도 실데이터에선 폭발

현재 same_ip(7,812)가 used_ip(15,197)보다 작은 것은 **아직 계정이 IP에 분산돼 있어서**다
(대부분 IP가 N=1). 그러나 성질은 이차이므로, 실데이터에서 콜센터 IP의 N이 커지면 그 항이
제곱으로 뛴다:

  최다 IP **N=83 → 3,403쌍**.  N이 2배(166)면 → **13,695쌍 (4배)**.
  콜센터가 300계정을 공유하면 **그 IP 하나로만 44,850쌍**.

즉 계정이 2배 늘면 원본 used_ip 는 2배지만, 집중된 IP의 same_ip 는 **4배**로 벌어진다.

## 4. 저장의 추가 비용 (규모 외)

- **중복**: same_ip 는 `used_ip` 두 개에서 파생되는 정보다. 원본이 있으면 언제든 계산 가능 —
  저장하면 원본과 파생이 이중 관리된다.
- **갱신 부담**: 계정의 `used_ip` 가 하나 바뀌면, 그 계정이 속한 **모든 same_ip 쌍**을
  재계산해야 한다(N개 계정 IP면 N−1개 엣지 갱신).
- **온톨로지 원칙**: 조합 폭발형 파생 관계는 **저장하지 않고 질의 시 유도**한다(query-time
  derivation).

## 5. 대안: 질의 유도 (엣지 없이 동일 결과)

직접 엣지 없이 vt_ip 를 매개로 계정 쌍을 유도한다 — 결과·수치가 same_ip 저장과 동일하다.

```cypher
-- 같은 IP를 쓴 서로 다른 계정 쌍 (온디맨드)
MATCH (id1:vt_id)-[:used_ip]->(ip:vt_ip)<-[:used_ip]-(id2:vt_id)
WHERE id(id1) < id(id2)          -- (X,Y)/(Y,X) 중복 제거
RETURN id1, ip, id2
```

## 6. 검증 쿼리 (실행 가능, AgensGraph)

### ① IP별 계정 수·쌍 (§3.1 표 재현)
```cypher
MATCH (i:vt_id)-[:used_ip]->(x:vt_ip)
WITH x.ip_addr AS ip, count(DISTINCT i) AS n
WHERE n >= 2
RETURN ip, n, n*(n-1)/2 AS pairs
ORDER BY pairs DESC
```

### ② 산식 = 조회 일치 증명  (Σ C(Nₚ,2) == 경로 조회 path_count)
```cypher
-- (a) 산식: Σ C(N,2)
MATCH (i:vt_id)-[:used_ip]->(x:vt_ip)
WITH x, count(DISTINCT i) AS n
RETURN sum(n*(n-1)/2) AS pairs_by_formula;   -- = 7812

-- (b) 경로 조회: 실제 쌍 열거
MATCH (a:vt_id)-[:used_ip]->(x:vt_ip)<-[:used_ip]-(b:vt_id)
WHERE id(a) < id(b)
RETURN count(*) AS pairs_by_path;            -- = 7812  (a)와 일치
```
→ **두 값이 7,812 로 일치**. "산식으로 예측한 폭발량"이 곧 "실제 조회량"임을 보인다.

### ③ 편중(상위 IP 기여율)
```cypher
MATCH (i:vt_id)-[:used_ip]->(x:vt_ip)
WITH x, count(DISTINCT i) AS n WHERE n>=2
WITH x, n*(n-1)/2 AS pairs
RETURN pairs ORDER BY pairs DESC LIMIT 10;   -- 상위 10개 합 = 전체의 70%
```

## 7. 결론

- `same_ip` 직접 엣지의 부재는 **결함이 아니라, Σ C(Nₚ,2) 의 이차·편중 성질을 피한 설계**다.
- 조회는 vt_ip 매개 온디맨드로 **동일하게** 충족된다(§5, 7,812쌍 실증).
- 수사 수요(공범·다중계정·위장계정 실사용자 특정)는 오히려 높다.
- 성능이 우려되면 답은 전면 엣지화가 아니라 **결과 캐시** 또는 **고공유 IP만 선별 사전계산**이다.
