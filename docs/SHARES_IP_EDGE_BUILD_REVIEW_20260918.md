# shares_ip 엣지 통합그래프 구축 — 검토 (구현 전 결정 근거)

> 공유-IP projection([[SHARED_IP_PROJECTION_DESIGN_20260918]])을 `shares_ip` 엣지로 실체화할지
> 결정하기 위한 검토. **구현 아님 — 판단 근거만.** 수치는 로컬 `ccop_ep_integrated` 실측(2026-09-18).

---

## 1. 결론 요약

- **구축 자체는 가능**하고, 가중+임계로 규모도 관리된다(w≥1.0 시 80개, +0.3%).
- 다만 **온톨로지 정경 확장(파급)** 과 **갱신 로직** 비용이 따르고, 조회는 온디맨드로도 되므로
  **"반복 그래프 분석/T2C 간소화" 라는 활용 시나리오가 확실할 때** 구축하는 것이 맞다.
- 지금 단발 조회 목적이면 **온디맨드 유지**를 권장하고, 구축은 활용이 구체화되면 착수.

## 2. 구축 시 결정해야 할 5가지

### ① 온톨로지 정경 추가 (필수 — 안 하면 감사 위반)

`shares_ip` 는 현 정경(엣지 72종)에 **없다**. 실체화하면 감사(`audit_ontology_v48`)가 "정경 외
엣지"로 잡는다. 따라서 SoT 에 등록해야 한다.

유사 엣지 재활용 가능성 검토(전부 부적합 → 신규 등록이 맞음):

| 엣지 | 정의 | shares_ip 로 쓸 수 있나 |
|---|---|---|
| `same_as`(활성) | Person\|DigitalID\|Phone 간 **동일 실체** | ✗ 과단정 — IP 공유는 "정황"이지 "동일인 확정"이 아님 |
| `linked_to`(활성) | Any→Any **범용 연결** | ✗ 의미 소실 — 무슨 근거의 연결인지 사라짐 |
| `clusters_with`(deprecated) | Petition→Petition 유사진정서 | ✗ 대상·의미 다름, 폐기 예정 |

→ **신규 `shares_ip` 등록 필요**. 제안 정의:
```
shares_ip: domain=DigitalID, range=DigitalID, label_ko='IP공유',
           derived=True(파생: used_ip 2개에서 유도),
           properties=[weight, shared_ips, source_id]
           meaning='두 계정이 공통 IP를 사용(동일인·공범·공용망 정황)'
```
비용: SoT + 전달본 재생성 + 감사 도구(자동) + T2C 프롬프트. **온톨로지 변경 = 파급**(vt_case
canonical 변경과 동급 작업).

### ② 임계 선택 (규모 결정)

| 시나리오 | shares_ip 엣지 | 총엣지(26,085) 대비 | 평가 |
|---|---|---|---|
| 전체(콜센터 포함) | 7,061 | +27% | ✗ 과다·노이즈 |
| 콜센터 제외(Nₚ≤50) | 3,670 | +14% | △ |
| 콜센터 제외 + w≥0.5 | 1,207 | +4% | ○ 넓게 |
| **콜센터 제외 + w≥1.0** | **80** | +0.3% | **◎ 밀접만** |
| 콜센터 제외 + w≥2.0 | 10 | +0% | 최밀접만 |

→ 권장 **w≥1.0(80)** 또는 **w≥0.5(1,207)**. 콜센터 제외는 필수. 전체 실체화는 금지.

### ③ 방향성 (대칭 관계)

`shares_ip` 는 대칭(a–b = b–a)이나 AgensGraph 엣지는 방향형. 두 방식:
- **단방향 저장**(`id(a)<id(b)` 로 1개) — 저장 절반, 조회 시 양방향 매칭(`-[:shares_ip]-`) 필요
- **양방향 저장**(2개) — 조회 단순하나 엣지 2배
→ 권장: **단방향 저장 + 무방향 조회**(`(a)-[:shares_ip]-(b)`).

### ④ 갱신 부담

`used_ip` 가 바뀌면 관련 `shares_ip`·`weight` 재계산 필요. 현실적 처리:
- **통합그래프 재빌드에 편입** — `build_integrated_graph.py` 마지막에 shares_ip 생성 단계 추가.
  재빌드가 곧 갱신(현재도 EP 데이터는 재빌드로 관리). 증분 갱신은 불필요.
- IP 희귀도(`shared_id_cnt`)도 이때 함께 계산.

### ⑤ 운영 DB 리스크

생성 쿼리가 `(vt_id)-[used_ip]->(vt_ip)<-[used_ip]-(vt_id)` **경로 순회**라, 운영 개발빌드
(2.16-devel)에서 크래시 패턴에 근접(WHERE 가 id 비교라 트리거와 다르긴 함). **로컬/안정판에서만
생성**하고, 운영 반영은 안정판 교체와 함께. (로컬 검증은 이미 통과)

## 3. 득실 비교 — 실체화 vs 온디맨드

| | 실체화(shares_ip 엣지) | 온디맨드(현재) |
|---|---|---|
| 단발 조회 | 1-hop, 빠름 | 2-hop 경로, 충분히 빠름(1.3초) |
| 반복 그래프 분석(중심성·군집) | **유리** — 계정망 직접 알고리즘 | 매번 투영 재계산(비쌈) |
| T2C 질의 | "IP 공유 계정" 1-hop, 프롬프트 간단 | 2-hop 경로 생성 필요(현재도 됨) |
| weight 순위(밀접 쌍) | **속성으로 즉시** | 매번 계산 |
| 온톨로지 | **정경 확장 필요(파급)** | 불필요 |
| 갱신 | 재빌드 편입 | 없음 |
| 저장 | +80~1,207 엣지 | 0 |

**실체화 이득이 분명한 경우**: ① 계정 군집 분석(같은 IP망 클러스터) ② 밀접 쌍 랭킹을 자주 조회
③ T2C 가 IP 공유를 1-hop 으로 다뤄야 할 때.
**온디맨드로 충분한 경우**: 단발 "이 계정과 같은 IP 쓴 계정" 조회 위주.

## 4. 권장 결정

1. **지금**: 활용 시나리오(군집분석·랭킹 상시조회)가 확정되지 않았다면 **온디맨드 유지**.
   온디맨드도 검증 완료(7,812쌍, 1.3초)라 기능 공백 없음.
2. **구축한다면**: 아래 순서로 (vt_case canonical 변경과 동급 작업량)
   - a. 온톨로지 SoT 에 `shares_ip`(derived, DigitalID→DigitalID, weight/shared_ips) 등록
   - b. `build_integrated_graph.py` 에 생성 단계 추가 — 콜센터 제외(Nₚ≤50) + **w≥1.0** 단방향
   - c. 전달본·감사·T2C 프롬프트 반영, 로컬 재빌드 검증
   - d. 운영 반영은 안정판 교체 시
3. **임계**: 처음엔 **w≥1.0(80개)** 로 보수적 시작 → 활용 보며 w≥0.5(1,207)로 확대.

## 5. 미결 — 사용자 판단 필요

- **활용 시나리오가 무엇인가** — 군집분석/랭킹 상시조회면 구축 이득. 단발조회면 온디맨드.
- **임계** — 밀접만(w≥1.0, 80) vs 넓게(w≥0.5, 1,207).
- 구축은 온톨로지 파급 작업이라, **착수 결정 후** 진행.

## 부록 — 검토 쿼리 (읽기 전용, 저장 안 함)

```cypher
-- 임계별 예상 엣지 수 (콜센터 제외 + w 하한)
MATCH (a:vt_id)-[:used_ip]->(x:vt_ip)<-[:used_ip]-(b:vt_id) WHERE id(a)<id(b)
MATCH (x)<-[:used_ip]-(u:vt_id)
WITH id(a) AS pa, id(b) AS pb, id(x) AS ip, count(DISTINCT u) AS Np WHERE Np<=50
WITH pa, pb, sum(1.0/Np) AS w WHERE w>=1.0
RETURN count(*);   -- w>=1.0: 80 · w>=0.5: 1207 · w>=2.0: 10
```
