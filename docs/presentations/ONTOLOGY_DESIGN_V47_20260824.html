왜 온톨로지인가 수사 질문은 곧 관계 질문 — 스키마 없이는 자동화도 없다

기존 방식의 한계 (i2 등)

  • 분석가가 문서를 읽고 수동 마크업 — 사건마다 표기가 제각각
  • 표준 스키마 부재 → 사건 간 비교·통합·재사용 불가
  • "이 IP를 누가 공유했나" 같은 질문에 사람이 직접 그림을 그려야 함

CCOP 접근 — 온톨로지가 공통 계약

  • Text2Cypher: 자연어 질문 → 스키마 제약 Cypher 생성
  • ETL 적재: RDB·CSV → 그래프 변환의 라벨·방향·멱등 기준
  • 문서 추출: LLM 추출 결과의 할루시네이션 차단 기준
  • 시각화: 노드·엣지 스타일 단일 진실(SSOT)

온톨로지는 설계 문서가 아니라 런타임 계약이다 — 스키마가 표현 못 하는 수사 질문에는 시스템 전체가 답하지 못한다.

레이어 색상은 제품 시각화 표준(VISUAL_STYLE_V40)과 동일 — 발표 자료와 실제 화면이 같은 언어를 씀

핵심 사상 ① 식별자는 속성이 아니라 노드다 전화·계좌·IP를 인물 속성으로 뭉치면 그래프의 존재 이유가 사라진다

인물 카드 방식 (속성 뭉치기)

인물{ 전화:[...], 계좌:[...], IP:[...] }

  • 두 인물이 같은 IP를 쓴 사실을 표현할 방법이 없음
  • 통화망(contacted)·자금흐름(from/to_account) 엣지를 걸 수 없음
  • 크로스-문서 동일인 통합(sameAs)은 노드 기준 — 속성이면 불가

POLE 분리 방식 (CCOP)

(인물)-[used_ip]→(IP)←[used_ip]-(인물)

  • 공유 자원이 교차점으로 드러남 — 공범·조직 탐지의 단서
  • 실증: 공유 IP 122.54.197.65 하나가 가입자 문서 3건을 연결해 조직 구조를 노출 (2차년도 검증)
  • 저장은 분리 노드, 화면은 인물중심 뷰 — 표시 레이어에서 해결

핵심 사상 ② 행위는 엣지가 아니라 이벤트 노드다 Reification — 국제 표준(CASE·Participation Pattern) 정렬

vt_bacnt
출금계좌 from_account→ vt_transfer
이체 (시각·금액) to_account→ vt_bacnt
입금계좌 via_ip→ vt_ip
접속 IP
  • 왜? 행위 하나에 시각·금액·수단·IP 등 다면 속성이 붙고, 참여자가 3개 이상(계좌 2 + IP)일 수 있다 — 엣지 하나로는 못 담음
  • 이중 표현 — 요약 직접 엣지(transferred_to·contacted) 병행: 3단계+ 자금흐름 추적 같은 다단계 경로탐색은 직접 엣지가 빠름
  • V4.6에서 직접 엣지에 이체시각 기간집계를 추가해 시간 조회까지 지원

  • used_ip·has_account·owns_phone에 유효구간 실반영·백필

재계산 순서도 규칙으로 고정 — sameAs 해소 후 실체(entity) 기준. 순서가 바뀌면 같은 데이터에서 다른 결론이 나온다.

Provenance — 증거 사슬 모든 엣지가 출처·신뢰도·검증 상태를 지닌다

엣지 공통 메타 (EDGE_META_SCHEMA)

  • 필수: edge_id(안정 ID) · source_id(vt_src 참조) · rec_created · creation_method
  • creation_method = manual | etl | ocr_ner | osint | inference
  • 출처는 vt_src 노드 + sourced_from 엣지로 정규화 — 전 레이어 수직 관통

신뢰도 3축

  • confidence 0.0~1.0 (1.0 = 공식 문서)
  • credibility 1~5 (GraphAware 기준)
  • verified — 주장 vs 확인의 구분. True면 수사관 ID·검증 일시 필수

추론으로 생긴 엣지와 공식문서 엣지가 그래프 안에서 구분된다 — 분석 결과를 법적 증거로 잇는 전제 조건.

엔티티 해소 — human-in-the-loop 자동은 후보까지, 확정은 수사관이

  • 식별자 형식 표준(NODE_ID_STANDARD) — 노드별 canonical 키 + id_format(평문/md5/sha256): OSINT 해시 데이터와 수사 평문 데이터의 cross-source 매칭 기반
  • sameAs 후보 자동 탐지 — 두 인물이 전화+계좌를 동시 공유하면 후보 생성(신뢰도 0.85), 단 review_required — 인물·조직의 자동 확정 금지
  • 미확정 표현 — is_anonymous 플래그 + traversal_policy=candidate_only(시각화 점선): 확정 전 후보가 분석 결과를 오염시키지 않도록 격리
  • 병합 방식 — 임의 ID를 실제 ID로 교체하지 않고 sameAs로 병합: 걸려 있는 엣지를 보존하고 해소 이력을 추적

동일인 오통합은 수사에서 가장 위험한 오류 — 자동화의 경계를 스키마에 명시한 것이 이 설계의 핵심이다.
