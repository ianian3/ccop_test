이체·통화 이벤트,
노드로 둘 것인가 엣지로 바꿀 것인가

계좌-계좌 이체·전화-전화 통화를 직접 엣지로 변경하는 안의 장단점과 전환 공수 분석

2026-07-28 · 코드베이스 실측 기반 (영향 파일 grep 전수조사 + 학습데이터 계량)

논점 정리

  • 현재 설계 — 이벤트 구체화(reification): 이체·통화가 노드이며, 양끝 개체와 2개의 엣지로 연결
  • 검토안 — 이체·통화를 계좌·전화 사이의 직접 엣지로 변경 (속성은 엣지 프로퍼티로)
  • 판단 기준 — ① 질의 단순성·성능 ② 네트워크 분석 정합성 ③ 증거 객체성·규격 호환 ④ T2C 학습 자산 보존 ⑤ 전환 공수

미리 보는 결론 — 전면 전환(3~4주+리스크)보다 "노드 유지 + 파생 요약 엣지" 하이브리드(3~5일)가 이득의 대부분을 흡수한다.

두 설계의 형태 이체 1건 기준: 노드 1 + 엣지 2 → 엣지 1

⚠️ 온톨로지의 Event 계층은 transfer·call만이 아니라 5종(+ access, msg, movement) — 2종만 바꾸면 "행위=노드" 원칙이 이원화됨 (ontology_service.py:834)

엣지화의 장점 질의·성능·분석 관점

  • Cypher 단순화 → T2C 유리 — 이체 1건 질의가 2홉 → 1홉. 자금흐름 추적이 (a)-[:transfer*1..5]->(b) 한 패턴 (현행 fund_flow는 10홉 경로 정의)
  • 그래프 규모 절감 — 이체 1건 = 노드1+엣지2 → 엣지1. 대량 통화기록에서 노드 수 급감 → 시각화·탐색 성능 향상
  • 시각화 모델 일치 — 현재 UI의 "이벤트 접기" 토글이 흉내 내는 형태가 원래 데이터 형태가 됨 → 이중 표현 유지보수 소멸
  • 네트워크 분석 정합 — 중심성·조직구조 분석이 계좌-계좌 동종 네트워크에서 바로 유효 (현재는 이벤트 노드가 끼어 차수 왜곡)
  • 표현력 문제 없음 — AgensGraph는 멀티그래프: 같은 계좌쌍 사이 이체 N건도 병렬 엣지 가능

엣지화의 대가 수사 도메인에서 치명적인 것들

  • n-ary 관계 상실 — 엣지는 끝점 2개뿐. 이체↔ATM·수표·사건, 통화↔사건 연계가 구조에서 속성으로 격하 → "이 ATM에서 발생한 이체 전부"가 그래프 탐색이 아닌 전체 엣지 속성 스캔이 됨
  • 증거 객체성 상실 — 이체·통화는 그 자체가 증거 단위: provenance(source_id·증거번호), sameAs/ER, 태깅 대상. 엣지는 다른 노드가 참조할 수 없음
  • T2C 자산 무효화 — 학습셋의 약 20%가 이벤트 노드 패턴. v42(86.6%)가 즉시 구식 → 재생성·재학습·재벤치 필수 (v43 catastrophic forgetting 전례)
  • 외부 규격 파급 — 파트너 데이터 표준·OSINT 제출 규격이 이벤트 노드 기준으로 이미 배포 (문서 12건) → 외부 기관 재협의
  • 검증 필요 — AgensGraph 엣지 속성 인덱스 지원·성능 (금액·일시 필터가 전부 엣지 속성으로 이동)

전면 엣지화는 "이벤트 속성·제3자 연계가 거의 없는 순수 네트워크 분석" 용도에서만 정당화된다.
CCOP는 그 반대(증거 중심) 도메인 — 하이브리드로 이득의 90%를 1/5 공수에 얻는 것을 권장.
