## 2. 핵심 검증 포인트

### 2.1 스키마 제약이 할루시네이션을 실제로 억제
온톨로지 밖 엣지 타입 **13건 폐기**: `file_in`(3), `evident_in`(3), 타입 누락(7).
→ Text2Cypher와 동일 철학(arXiv 2505.05118, schema-guided)이 **문서 추출에도 유효**함을 확인. 검증기(`validate`)가 온톨로지 25노드/66엣지 밖 타입을 차단.

### 2.2 엔티티 해소가 청크 간 중복을 통합
전화번호 정규화 키(하이픈 제거)로 `01084573455`가 여러 청크에 등장해도 **단일 노드**로 통합. 관계는 청크 로컬 `local_id` → 전역 키로 리매핑 후 중복 제거(원시 관계 다수 → 고유 13).

### 2.3 max_tokens 절단 문제 해결 (0/0 → 정상)
초기 실행이 0/0이었던 원인은 v46 무능이 **아니라** 3,200자 청크의 응답 JSON이 `max_tokens=2048`에서 잘려 파싱 실패한 것. 조치: **청크 1,200자 축소 + max_tokens 4096 + 잘린 JSON 복구(`_salvage_array`)**. → 전 청크 정상 추출.

## 3. 품질 — 정직한 한계

PoC는 "동작함"을 입증했으나, 운영 품질까지 보증하지는 않는다. 관찰된 오류와 원인:

| 관찰 | 예시 | 원인 | 대응 |
|---|---|---|---|
| **플레이스홀더 값 추출** | `vt_psn{name:피의자1}`, `vt_ip{ip_addr:"IP 주소"}` | **시나리오 문서 자체가 템플릿** — 실명/실IP 대신 역할·라벨 사용. 추출은 원문에 충실 | 실제 수사보고서엔 실값 존재(01084573455·203.0.113.5는 정확 추출됨) |
| **관계 방향 오류** | `vt_bacnt-[from_account]->vt_case` (계좌→사건은 부적절) | v46가 방향·도메인 혼동 | 설계 ④ `_fix_relation_direction`(ai_service) 재활용 미적용 — 다음 스프린트 |
| **reification 엣지 편향** | `accessed_from`(6) 과다, `access_via`(2) 과소 | 알려진 v42/v46 학습 편향(메모리 기록) | few-shot 주입 or v47 |
| **엔티티 해소 과통합 위험** | 동일 이름 다른 인물 | fuzzy 매칭 미적용(현재 식별자 정확일치만) | 설계 ④ `sameAs review_pending`(자동확정 금지) |

**핵심 판단**: v46(Text2Cypher 특화 소형모델)는 **온프레미스 추출 폴백으로 실용 가능** — 실제 식별자는 정확히 뽑고 스키마도 준수. 단 관계 방향·역할 정밀도는 gpt-4o 대비 낮음. 설계 원안대로 **운영 정확도는 gpt-4o, 폐쇄망은 v46**의 이원 전략이 타당함을 실측으로 재확인.
