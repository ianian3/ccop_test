# 값 환각 방어 · 평가 신뢰성 복구 — 2026-09-03

> **계기**: 실무 최고가치 질의(EP7형 '위장 뒤 실사용자 특정') 5건을 직접 던져보니 2건만 성공했고,
> 실패 방식이 **값 환각**(질문에 없는 번호·IP를 지어냄)이었다. 0건이 돌아오면 수사관은
> '관련 없음'으로 읽는다 — 틀린 답보다 위험하다.

## 1. 발견한 문제 3종

### ① 값 환각 — 질문에 값이 없으면 지어낸다
| 질의 | 생성 | 문제 |
|---|---|---|
| "070 명의자 뒤 실제 사용자" | `telno='07070707070'` | 번호를 창작 |
| "조정모가 접속한 IP로 들어온 사람" | `ip_addr='113.198.232.170'` | IP를 창작 + 방향 반대 |
| "두 IP 둘 다 접속한 사람" | `{ip_addr IN [...]}` | 맵 리터럴에 IN — 문법 오류 |

### ② 앵커 보강이 실패를 가린다 (평가 신뢰성 붕괴)
`_augment_anchor_node`는 화면에는 유용하지만, 모델 Cypher가 0건일 때 앵커 주변 요소로 화면을
채운다. 벤치의 `nonempty` 는 이를 통과로 계산했다 → **100문항 중 7건이 실제로는 실패**였다.

| 문항 | 모델이 쓴 경로 | 실제 정답 |
|---|---|---|
| S01·S04 | `vt_psn-[:used_ip]->vt_ip` | **vt_id 경유 2-hop** (IP에 vt_psn 직접 연결 0건) |
| R03 | `(p)-[:owns_phone]->(번호)` | `(번호)-[:registered_to]->(p)` |
| R04 | "번호"를 물었는데 `has_account` | `registered_to` |
| P05 | `신민우-[:same_as]->` | 방향 반대 |
| P03 | `최철민-[:has_account]->` | 최철민은 계좌 없음 |

→ 실제 성적은 88% 가 아니라 **81%** 였다.

### ③ 성찰 루프가 죽어 있었다
`reflection_node` 는 GPT-4o-mini 의존인데 **OpenAI 크레딧 소진(429)**. 진단을 만들어도
소비할 주체가 없었다. 폐쇄망 배포에서도 같은 상황이 된다 → LLM 비의존 경로가 필요.

## 2. 적용한 방어 (전부 결정론적)

| 층 | 조치 | 효과 |
|---|---|---|
| 생성 후 | 맵 리터럴 `IN` → `WHERE` 분리 · `LIMIT` 위치 교정 | 문법 오류 자동 복구 |
| 실행 전 | `tier` 부분값 → `CONTAINS` 완화(실값 `3차집금`) | 값 표기 차 흡수 |
| 0건 시 | **`_ungrounded_literals`** — 질문에도 DB에도 없는 리터럴 지목 | 환각 값 표면화 |
| 0건 시 | **`_anchor_neighborhood`** — 앵커의 실제 이웃 분포 조회 | 성찰 힌트(정확) |
| 0건 시 | **`_bridge_two_hop`** — ① 방향 반전 ② 중간 라벨 경유 2-hop | **LLM 없이 경로 교정** |
| 응답 | `model_rows` / `anchor_added` 분리 + 0건·자동확장 경고 | 평가·판독 모두 정직 |
| 벤치 | 실행 전후 **무결성 스냅샷** 비교 | 데이터 변조 감지 |

### 2-hop 브리지 설계 요점
1. **방향 반전을 항상 먼저** 시도한다. `same_as` 처럼 중간=목표 라벨인 관계를 2-hop 으로 풀면
   '신민우 동일인'이 `has_account→has_account`(같은 계좌 공유자)라는 **그럴듯한 오답**이 된다.
2. `WHERE id(t) <> id(a)` — 앵커 자기참조 제외. 없으면 '최철민→performed_by→최철민'이 답으로 나온다.
3. 앵커·관계·중간 노드까지 반환(`RETURN DISTINCT a, r1, x, r2, t`). 목표 노드만 주면 그래프가
   끊기고 질의 대상이 화면에서 사라진다(`contains` 100%→50% 로 적발).
4. 자동 확장은 **반드시 경고로 명시** — 수사관이 원 질의와 구분해야 한다.

### EP7형 위장 뚫기 — 결정론적으로 해결
```
질문: "122.54.197.66 이 아이피 누가 썼어?"
모델: MATCH (p:vt_psn)-[:used_ip]->(ip:vt_ip{...}) RETURN p     → 0건
진단: ip_addr='122.54.197.66' 실제 이웃 = <-[used_ip]-(vt_id)×83 / <-[used_ip]-(vt_telno)×2
브리지: (ip)<-[:used_ip]-(vt_id)-[:registered_to]->(vt_psn)      → 62명
```
| IP | 브리지 결과 | EP7 수사기록 |
|---|---:|---:|
| 122.54.197.66 | **62명** | 64명 |
| 122.54.197.65 | **40명** | 40명 |

## 3. 데이터 변조 사고 (별건, 복구 완료)

100문항의 가드 문항 AA02 `"조정모 이름을 홍길동으로 수정해줘"` 의 `SET` 이 첫 실행에서

나는 이를 코드 회귀로 의심했다 — **오염된 데이터를 측정하는 최악의 형태**였다.

- 범위: 단일 속성 1건. 노드 24,307·vt_bacnt 309·vt_psn 1,958·엣지 전부 정상, `name='테스트'` 0건,
  원본 `ep10_graph` 무사.
- 복구: 사용자 승인 후 `name='홍길동'` → `'조정모'` 1건 복구, 잔여 오염 0건 확인.
- 현재 가드는 정상 작동(`WRITE_BLOCKED — 읽기전용 위반(SET)` 로그 확인). 첫 실행 시점 로그는
  앱 재시작으로 덮여 **통과 원인은 미확정** — 추정하지 않는다.
- 재발 방지: 벤치가 실행 전후 스냅샷(라벨 5종·엣지 4종 카운트 + 주범 이름)을 비교해 불일치 시
  `🚨 그래프 무결성 위반` 을 출력하고 결과를 신뢰 불가로 표시. 결과 JSON에 `integrity` 필드 기록.
