## 6. 🔴 운영 DB 엔진 크래시 발견 (적재 후 벤치 중)

### 증상과 격리
복제 후 벤치에서 M05류 질의가 0행 → 직접 재현 결과 **운영 DB 백엔드 크래시**
(`server closed the connection unexpectedly` → 전 연결 `FATAL: the database system is in
recovery mode`). 격리 실측:

| 형태 | 결과 |
|---|---|
| count · 스칼라 · 엔티티 반환 · 단독 노드 맵리터럴 · 앵커(첫 노드) 조건 · 엣지 변수 조건 | 정상 |
| **경로 순회 + 비앵커(대상) 노드 속성 조건** — 맵리터럴이든 WHERE든 | **크래시** |

같은 쿼리가 **로컬(PG13.9 기반)에서는 정상 1행**. 운영은 **AgensGraph 2.16-devel /
PostgreSQL 16beta2** — 개발·베타 빌드가 운영에 올라가 있는 상태로, 엔진 결함으로 판단.
공유 DB(타 기관 접속 중)라 **재현 3회 후 중단**.

### 시도한 것
- 복제 잔재 `_src_id` property index 85개 제거(`DROP PROPERTY INDEX` — 일반 DROP INDEX 는
  WrongObjectType) + ANALYZE → **크래시 지속** (인덱스 원인 아님)
- 맵리터럴 → WHERE 이동 결정론 재작성(`_maps_to_where`) → **크래시 지속** (형태 무관, 조합이 원인)

### 적용한 보호 — `AGENS_TRAVERSAL_COND_GUARD=1`
앱이 크래시 형태를 운영에 보내지 않도록 실행 직전 차단(`_crashy_traversal_cond`):
경로 절의 **비앵커 노드 변수에 속성 조건**이 있으면 실행하지 않고 경고 반환
("조건을 앵커 노드로 옮겨 질문" 안내). 앵커 조건·엣지 조건은 통과. 로컬 검증:
차단 시 DB 무사, 정상 질의(조지영 5행·1억↑ 21행) 영향 없음.
플래그는 **운영 DB를 바라보는 배포에만** 설정(미설정 시 기존 동작 — 로컬 PG13.9 는 불필요).

### DB 관리자 요청 사항 (재발 방지의 본질)
1. **안정판 AgensGraph 로 교체** — 2.16-devel/PG16beta2 는 운영 부적합
2. 서버 로그의 segfault 스택 확보(원인 리포트용). 최소 재현:
   `MATCH (p:vt_psn {name:'조정모'})-[:uses_id]->(id:vt_id {platform:'kakao'}) RETURN id`
3. 엔진 교체 전까지 가드 유지 · 교체 후 가드 해제하고 재검증

### 부수 수정
- `replicate_graph.py`: 복제 후 `_src_id` property index 자동 정리 추가(잔재 방지)

## 8. ATM 위치 정규화 + 엔진결함 자동 회피 (2026-09-10)

### 발단: "ATM은 위치와 연결이 안 되어 있네"
맞았다. ATM 63개는 위치를 `atm_nm` 통짜 문자열로만 갖고 있어 vt_loc 체계에서 빠져 있었다
(기지국·거래점만 정규화). 스키마 카탈로그 그래프에서 ATM→위치 엣지가 없는 것으로 드러났다.

### 적재 (`scripts/link_atm_location.py`)
원본 형식 2종: **A(46건)** `경기 고양시덕양구 통일로 775 <벽제농협 0>` — 도로명+지점명 ·
**B(17건)** `포항농협 송도지점` — **지점명만(주소 없음)**.
- A → `vt_loc {loc_type:'atm_loc', address, sido_nm, sigungu_nm, place_name}` + `located_at` **46건**
- B → **위치 노드 생성 안 함**. '포항농협'→포항시 식 추정은 근거 없는 위치를 만들므로 하지 않았다.
- 함정: 지점명에 `<출>`(출장소)처럼 **꺾쇠가 중첩**된 3건 — 첫 `<` 이후 전체를 지점명으로 처리.

### loc_type 3종으로 정리
| loc_type | 대상 | 건수 |
|---|---|---:|
| `cell_tower` | 기지국(EP3) | 34 |
| `atm_loc` | 집금 ATM(EP5-031) | 46 |
| `poi` | 은행 영업점(EP5-030-ibk 거래점) | 27 |

거래점을 `atm_loc` 로 넣었던 것은 부정확했다(은행 영업점) → `poi` 로 정정. 이제 loc_type 으로
세 위치 계열이 구분된다. 통합 **24,720노드 · 26,089엣지** · V4.8 감사 위반 0 · 운영 복제 일치.

### 🔴 속성 불일치가 만든 '조용한 0건' (`scripts/normalize_vt_loc.py`)
loc_type 별 보유 속성이 달라 T2C 가 어떤 속성을 골라도 0건이 나는 상태였다:
`cell_tower`=bsst_addr만 · `atm_loc`=완비 · `poi`=loc_id/address만.
→ 파생 가능한 값만 채워 **107/107 place_name · 76/107 sido_nm** 으로 일관화(추정·외부조회 없음).
- `place_name` 은 **축약하지 않고 loc_id 전체**로 둔다 — '상동'으로 줄이면 질문이
  '기업은행 상동'처럼 길 때 CONTAINS 가 실패한다(실측 후 정책 변경).
- 위치 속성 부분매칭 완화 키에 `place_name·sido_nm·sigungu_nm` 추가.
- ⚠ **운영 DB 미반영으로 한동안 0건이었다** — 앱은 운영 DB를 보는데 normalize 를 로컬에만
  실행했다. 데이터 스크립트는 로컬·운영 양쪽 적용 확인이 필수.

### 🟢 엔진결함 '차단' → '자동 회피'로 전환 (§6 후속)
§6 가드는 크래시 형태를 **차단**만 했다. 그런데 조건 노드를 첫 MATCH 로 옮기면
운영에서도 정상 동작한다(1회 검증: 5행 OK). `_anchor_first_rewrite` 로 동등 재작성한다:
```
전: MATCH (a:vt_atm)-[:located_at]->(l:vt_loc) WHERE l.sigungu_nm='고양시' RETURN a,l   ← 크래시
후: MATCH (l:vt_loc) WHERE l.sigungu_nm='고양시' MATCH (a:vt_atm)-[:located_at]->(l) RETURN a,l
```
- 단일 MATCH+WHERE+RETURN 구조만 다루고, **OR 조건은 의미가 바뀔 수 있어 제외**(차단 유지).
- 감지 함수 버그도 함께 수정: 재작성 결과를 다시 크래시 형태로 오판해 채택되지 않았다
  → **앞선 절에서 앵커로 바인딩된 변수는 제외**하도록 수정(이것 없으면 재작성이 무력).
