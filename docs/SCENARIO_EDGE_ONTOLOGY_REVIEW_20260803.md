## 2. 핵심 판단 — "직접 엣지 vs 이벤트 reification"

앞선 온톨로지 검토(`CCOP_ONTOLOGY_V4.1_REVIEW.md`)에서 CCOP의 **이벤트 reification**이 CASE·Participation Pattern **국제 표준**임을 확인했습니다. 시나리오는 수사관 관점의 "직접 연결"로 표현했지만, **행위성 엣지를 그대로 직접 추가하면 그 설계 철학을 훼손하고 온톨로지를 팽창**시킵니다. 따라서 성격별로 갈라야 합니다:

- **행위성**(접속·이체·출금·통화·위치) → **이벤트 노드**(vt_access·vt_transfer·vt_call) 경유가 정석 → 직접 엣지 대신 이벤트 참여·occurred_at 확장
- **속성적 연결**(소유·유사·지인·식별자 연결) → **직접 엣지**가 자연스러움

## 4. 적용 권고 (우선순위)

**🟢 1순위 — 즉시 추가 가능 (직접 엣지, 저위험 · 5개)**
패턴 C·D. 온톨로지 철학과 무충돌, ETL·Text2Cypher 영향 최소:
- 계좌↔인증서ID, 전화↔계정, 계정→게시물 (식별자 연결)
- `sameAs`를 vt_id로 확장 (계정 유사성)
- `knows` 신규 (사회관계 — 지인)

**🟠 2순위 — 이벤트 reification 확장 (설계 검토 · 11개)**
패턴 A·B·E. 정석이나 ETL 파이프라인·Text2Cypher 프롬프트 영향이 있어 별도 설계 필요:
- 접속류(telno/id/bacnt→IP): `vt_access` 이벤트 참여 확장
- 금융류(crypto·atm): `vt_transfer` 확장 + `vt_atm` 고아노드 해소
- 위치류(telno→loc): 이벤트 `occurred_at` 확장

**🔴 3순위 — 노드 신규는 신중 (1개)**
"키워드"(마약 은어)는 `vt_keyword` 노드화보다 **`vt_msg`의 속성/태그**가 적합할 수 있음 — 노드 남발 방지.

## 5. 리스크

- **스키마 팽창 ↔ 방금 개선과 상충**: 직접 엣지 16개 무분별 추가 시 60→76엣지로 커져, 방금 완료한 **스키마 pruning(+5.5p) 효과를 잠식**합니다. 선별 필수.
- **데이터 근거 갭**: 계좌내역 샘플엔 **IP 컬럼이 없어**(입출구분·계좌주·거래액·상대은행만) No.5(bacnt-ip)는 별도 소스(모바일뱅킹 로그)가 선행돼야 합니다.
- **2차년도는 정형 데이터가 아님**: EP1~10은 영장·수사보고·카톡 등 **문서(PDF/hwp)** 중심 — 접속 역조회(No.20~23)의 근거이나, ETL 적재는 문서 파싱(docling 등)이 전제.
