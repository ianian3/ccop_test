# 인물중심 노드셋 생성 규칙 — 온톨로지 정합 검토

> **작성일**: 2026-08-07
> **대상**: 인물중심 노드셋 생성 규칙(개인/법인 노드셋 + 미확정 ID 처리)
> **기준**: CCOP 온톨로지 V4.5 (POLE 6레이어, 노드 25종·엣지 71종)
> **결론 한 줄**: 의도(수사관의 인물중심 정리)는 타당하나, 식별자(전화·계좌·IP 등)를 **속성으로 뭉치면** 그래프의 핵심 가치(공유자원 탐지·관계분석·자금흐름·엔티티해소)를 잃는다. **저장은 분리 노드, 표시는 인물중심 뷰**를 권한다.

---

## 1. 규칙 요약

- **개인 노드**: id=주민번호, label=이름, 속성=나이·직업·전화번호(복수)·계좌번호(복수)·자택주소·직장주소·가상자산지갑·SNS id(복수)·닉네임(복수)·사이트url(복수)·범죄ip(복수)·이메일(복수)
- **법인 노드**: id=사업자번호, label=법인명, 속성=법인대표(이름·주민번호)·전화번호(복수)·계좌번호(복수)·주소·지갑·SNS id(복수)·사이트url(복수)·닉네임(복수)·범죄ip(복수)·이메일(복수)
- **미확정 ID**: 주민번호/사업자번호 미상 시 임의 값을 ID로 부여하고 **색을 다르게 한 노드** 생성, 확인되면 교체.

## 2. 핵심 이슈 — "속성 뭉치기" vs "엔티티 분리(POLE)"

규칙은 전화·계좌·IP·이메일·지갑·SNS(복수)를 **인물/법인 노드의 속성**으로 둔다. CCOP 온톨로지는 이를 **독립 노드 + 엣지**로 분리한다. 이 차이가 그래프의 분석력을 좌우한다.

**분리해야 하는 이유 (실측 근거):**
1. **공유 자원으로 공범 탐지** — 2차년도 검증에서 공유 IP `122.54.197.65`가 서로 다른 **3명의 가입자를 연결**해 조직을 드러냈다. IP를 인물 속성으로 뭉치면 이 교차(공유)를 **표현 자체가 불가능**하다.
2. **관계의 주체** — 전화번호는 통화(`contacted`)의, 계좌는 이체(`from_account`/`to_account`)의 주체다. 속성이면 통신망·자금흐름 엣지를 걸 수 없다.
3. **엔티티 해소·크로스-문서 통합** — `sameAs`, 크로스-문서 통합(사법문서 4건에 걸친 동일 피의자 통합)은 **노드 기준**이다. 속성이면 불가.

→ 규칙대로 저장하면 그래프가 "인물 카드 목록"이 되어 CCOP의 핵심(관계 분석)이 소실된다.

## 3. 속성별 온톨로지 매핑 (분리 대상)

| 규칙의 속성 | CCOP 노드 + 엣지 | 분리 사유 |
|---|---|---|
| 전화번호(복수) | `vt_telno` + `owns_phone` | 통화망·공유번호 |
| 계좌번호(복수) | `vt_bacnt` + `has_account` | 자금흐름·공유계좌 |
| 범죄ip(복수) | `vt_ip` + `used_ip` | **공유 IP 공범탐지** |
| 이메일(복수) | `vt_email` + `uses_email` | 교차 사용 |
| SNS id·닉네임(복수) | `vt_id` + `uses_id` | 계정 해소(sameAs) |
| 가상자산지갑 | `vt_crypto` + 소유 엣지 | 자금 종단 추적 |
| 사이트url(복수) | `vt_site` + 엣지 | 사이트-IP 연계 |
| 자택·직장주소 | `vt_loc` + `located_at`/거주·근무 | 위치 공유 |
| **나이·직업·이름** | ✅ `vt_psn` **고유 속성** | 인물에 종속 — 분리 불필요 |
| (법인) 법인대표 | **별도 `vt_psn`** + `operates`/대표 엣지 | 대표는 독립 인물 |
| (법인) 법인 자체 | `vt_org` | 개인과 별도 유형 이미 존재 |

즉 "복수 속성"은 대부분 독립 노드로, 인물에 진짜 종속된 것(나이·직업)만 속성으로.

## 4. 좋은 점 — "임의 ID + 색 구분 + 확인 시 교체"

온톨로지와 정합하는 **좋은 패턴**이며 기존 개념에 연결된다:
- 미확정 노드 = `is_anonymous`(파생속성) + `sameAs` **`traversal_policy=candidate_only`**(V4.5, 점선 표시)
- V4.5 시각화도 미확정 `sameAs`를 **점선**으로 구분 — "색 다르게"와 동일 취지

**단, ID 교체 방식 주의**: 임의 ID를 실제 ID로 직접 바꾸면 걸린 엣지를 모두 재연결해야 한다. ID를 바꾸기보다 **`sameAs`로 실제 노드와 병합**하는 편이 안전하다(엣지 보존 + 해소 이력 추적).

## 5. 짚을 점 — `id = 주민번호`

주민번호를 노드 **id로 직접** 쓰는 것은 개인정보 최고 민감도라 위험하다. CCOP 표준은 `vt_psn` canonical을 **`psn_id`(내부 비식별 식별자)**로 두고 주민번호는 **마스킹/해시 속성**으로 보관한다(사업자번호 동일). id는 비식별, 주민번호는 검증용 속성.

## 6. 권장 — 분리 저장, 인물중심 표시

규칙의 의도는 타당하되, **저장 구조가 아니라 표시(뷰) 레이어**에서 달성한다:
- **저장**: POLE 분리 노드(`vt_psn` + `vt_telno`/`vt_bacnt`/`vt_ip`… + 엣지) → 관계 분석 가능
- **표시**: 인물 노드 클릭 시 연결 자원을 **"인물 카드"로 집계 표시**(에고 네트워크) → 수사관의 인물중심 직관 충족

→ 그래프 분석력(공유탐지·자금흐름·해소)과 인물중심 뷰를 **모두** 확보.

## 7. 조치 제안 (우선순위)

1. 규칙의 "속성(복수)"을 **분리 노드+엣지 매핑표(§3)**로 전환 — 저장 스키마 확정
2. `id`는 `psn_id`/`org_id`(비식별), 주민번호·사업자번호는 마스킹 속성
3. 미확정 ID는 임의 노드 + `sameAs candidate_only`(점선) — 확인 시 **병합**(ID 교체 아님)
4. 인물중심 카드 뷰(에고 네트워크 집계)를 표시 레이어에 별도 구현
