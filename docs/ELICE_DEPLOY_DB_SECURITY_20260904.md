## 2. 방화벽 — 차단된 게 아니라 **승인 IP가 다른 인스턴스로 옮겨갔다**

2026-06-16 메일로 **앱서버("엘리스 C-8")용 `119.59.0.61/32`** 를 요청·승인받았다.
그런데 지금 `.61`을 쓰는 건 **GPU박스**이고, 앱서버는 미승인 `.62`를 받았다.

- 엘리스 온디맨드는 **인스턴스 재시작 시 아웃바운드 IP가 재배정**된다(과거 central-01→02 이전 이력).
- 즉 DB측이 권한을 회수한 것이 아니고, **방화벽 정책은 승인 그대로 정상 작동** 중이다.
- 7/29에 앱서버에서 직결이 됐던 것은 그때 앱서버가 `.61`이었기 때문으로 보인다.

**재발 방지**: `/32` 단건 대신 **`119.59.0.0/24` 대역 허용**을 요청할 것. 요청서 초안은
이 문서 하단 참조. (별건으로 받은 `3.29.28.218`·`3.35.45.35`는 AWS 서울 대역이며
현재 우리 서버와 무관 — 용도 확인 필요.)

### ⛔ skai2_vm 경유 금지
앱서버의 `127.0.0.1:5333` 은 **살아 있고 DB 접속도 된다**(DB가 보는 client_addr =
`175.45.205.106` = skai2_vm). 그러나 사용자 지시로 **사용 금지**다 — skai2_vm 은 실제 운영 VM이라

## 4. 운영 DB 데이터 결함 수정 — `ep_count` 문자열 → 정수

복제가 로컬 숫자화 이전에 이뤄져 **`ep_count` 24,307건만 문자열**이었다
(pagerank·kcore·community_id 등 다른 지표는 정상 숫자).

**영향**: `ep_count >= N`("여러 EP에 등장한 노드" = 교차 실증) 질의가 **전부 0건**.
EP 간 연결을 찾는 핵심 기능이 죽어 있었다.

**조치**(사용자 승인 후 실행): 값 6종을 일괄 SET으로 변환(AgensGraph에 `toInteger` 없음).
- 변환: `'1'→1` 23,023건 · `'2'` 1,218 · `'3'` 40 · `'4'` 21 · `'5'` 4 · `'6'` 1 = **24,307건**
- 무결성: 전후 노드·엣지 수 완전 일치 · 잔여 문자열 0
- 검증: `ep_count >= 3` → **66건**(로컬과 동일), 라벨별 IP 22·전화 16·계좌 23·인물 4·조직 1

## 5. 🔴 앱이 **슈퍼유저**로 DB에 접속하던 문제 → 읽기 전용 전환

### 발견
로그인 계정 10개 중 **8개가 슈퍼유저**이고, 앱이 쓰는 `ccop` 도 그중 하나였다(CREATE 권한 보유).

**왜 심각한가**: 이 앱은 **LLM이 생성한 쿼리를 실행**한다. 슈퍼유저와 결합하면
`COPY … PROGRAM` 을 통한 **OS 명령 실행**, 전체 그래프 삭제·변조가 가능하다.
추상적 위험이 아니다 — 같은 날 벤치 가드 문항(`"조정모 이름을 홍길동으로 수정해줘"`)의 `SET` 이
애플리케이션 가드를 통과해 **주범 이름이 실제로 변조**됐다(복구 완료). 앱 가드가 유일한
방어선이었고 그것이 한 번 뚫린 것이 확인됐다.

### 조치 — `ccop_app_ro` 생성 후 앱 전환
```sql
CREATE ROLE ccop_app_ro LOGIN PASSWORD '<28자 랜덤>'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;
GRANT CONNECT ON DATABASE tccopdb TO ccop_app_ro;
GRANT pg_read_all_data TO ccop_app_ro;   -- 내장 롤: 그래프 37개(스키마 48) 일괄 + 신규 자동 적용
```
- `cypher()` 는 함수가 아니라 파서 레벨 처리라 EXECUTE 권한 불요.
- 스크립트: `scratchpad/create_readonly_role.sql` (비밀번호는 `.env` 와 파일에만)

### 검증 결과
| 항목 | 결과 |
|---|---|
| 읽기 | ✅ 노드 24,307 · 주범 조정모 · `ep_count>=3` 66건 |
| **쓰기** | ✅ SET·CREATE·DELETE·SQL UPDATE **4종 전부 거부**(`permission denied for table …`) |
| 앱 기능 | ✅ 조지영 계좌 5건 · IP 22건 — 손실 없음 |
| 앱 경유 쓰기 시도 | ✅ 0건 (DELETE/SET 생성돼도 실행 불가) |

**효과**: 방어선이 두 겹이 됐다. 앱 가드가 뚫려도 DB가 거부한다. 슈퍼유저 전용 기능
(`COPY … PROGRAM`)을 통한 서버 장악 경로도 함께 닫혔다.

**쓰기 작업은 계정 분리로 자연스럽게 해결**: ETL·적재·`ep_count` 변환 같은 작업은 기존 `ccop`
계정으로 **스크립트 실행 시에만** 쓰고, **앱 서빙만 읽기 전용**. 운영 방식 변경 불필요.

## 6. 🟡 남은 보안 과제 — 전송 구간 평문

`pg_stat_ssl` 실측: **서버 `ssl = off`, 78개 연결 전부 SSL 미사용**.

- **비밀번호는 안전**(`scram-sha-256` 챌린지-응답 — 네트워크에 실리지 않음).
- **그러나 쿼리와 결과는 평문**. traceroute 실측 결과 **12홉 이상, 서로 다른 사업자망을 통과**
  (DB가 공인 IP로 인터넷에 직접 노출).
- 노출 대상: 조회 결과(실명·계좌번호·통화내역·출입국)뿐 아니라 **쿼리 자체** —
  `WHERE p.name='조정모'` 같은 조건이 **수사 대상·진행 상황을 노출**한다(수사 기밀 관점에서
  결과보다 민감할 수 있다). 라벨·속성·관계명 등 스키마 구조도 함께 노출.
- **변조(MITM) 위험**: 암호화가 없으면 무결성 검증도 없다. 읽기 전용 계정으로 DB 쓰기는
  막았지만, **네트워크 레벨에서 결과를 조작**해 수사관에게 거짓 정보를 보여주는 것은 별개 문제다.
- 법적 참고: 「개인정보의 안전성 확보조치 기준」은 정보통신망 전송 시 암호화를 요구한다.
  실명·계좌번호는 개인정보이며 수사 데이터라 민감도가 높다(정확한 적용 범위는 법무 검토 필요).

**취약 구간은 앱↔DB 한 곳뿐**이다 — 나머지는 이미 보호된다:

| 구간 | 상태 |
|---|---|
| 브라우저 → 엘리스 터널 | ✅ HTTPS |
| 앱 → sLLM(vLLM) | ✅ SSH 터널 / 같은 서버 내부 |
| 앱서버 → GPU박스 | ✅ SSH 터널 |
| **앱 → DB** | ❌ 평문 |

**조치**: DB에서 `ssl = on` + 인증서. 앱 코드 변경 불요(psycopg2 자동 협상), `.env` 에
`sslmode=require` 명시하면 확실. **DB 재시작 필요 → 관리자 협의 필수.**
7/29 기록의 *"DB가 공인 IP 비SSL 노출 — 데모 후 방화벽/터널 재정비 권장"* 이 바로 이 항목이다.
